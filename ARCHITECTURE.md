# Architecture

How the Claude Skills Library is built. Read it before you change data flow, caching, routes or a shared module. What the product must do is in [PRD.md](PRD.md); how it looks is in [DESIGN.md](DESIGN.md).

Accounts, user skills, a marketplace, personal libraries and playbooks are being added phase by phase; [ROADMAP.md](ROADMAP.md) holds their target design. Everything below describes the code as it is, and each phase updates it when it changes the code.

## Bird's-eye view

A curated catalog of Claude Code skills, published as a mostly static Next.js site.

- **Input:** one hand-written TypeScript file per skill in `src/data/skills/`, plus repository stats from the GitHub REST API.
- **Output:** prerendered HTML pages and three plain-text or JSON endpoints, regenerated every 6 hours (ISR).
- **The catalog has no backend.** Search, filters, multi-select, the recommender, copy and download run in the browser on data already in the page.
- **Accounts have one:** Postgres on Neon through Drizzle, Better Auth for email and password, GitHub, two-factor and passkeys, and Upstash Redis for the Server Actions' rate limits. Only `/api/auth`, `/api/me/export`, `/api/skills/[id]/download`, the daily cleanup, the sign-in pages, `/dashboard/**` and the header's account menu reach it, and the menu loads only in a browser that has signed in before.
- **Community reads it ahead of time:** `/community`, `/u/[handle]` and `/u/[handle]/[slug]`, the published skills, are prerendered and revalidated (ISR) like the catalog, and the sitemap lists the public ones. They answer 404 until sign-up opens.

```text
src/data/skills/<slug>.ts ──► src/data/skills/index.ts      registry: skills[] + helpers
                                         │
api.github.com ◄── src/lib/github.ts ────┤                  one fetch per unique repo,
                                         │                  cached 6 h, null on any failure
                                         ▼
                  src/app/**   Server Components and route handlers
                  ├── HTML pages ──► client components: search, selection, recommender, copy, download
                  └── /skills.json · /llms.txt · /install-all.txt     serializers in src/lib/report.ts
```

## Code map

### `src/data/`

- `types.ts`: the `Skill` interface, `SkillCategory`, `InstallMethod` and `CATEGORY_LABELS`. Every entry, page and serializer depends on this schema.
- `skills/<slug>.ts`: one catalog entry per file, exported as `export const skill: Skill`.
- `skills/index.ts`: the registry. It imports every entry into `skills` (lists sort by GitHub stars, so array order only breaks ties) and exposes `getSkill`, `getFeaturedSkills`, `getCategoriesWithCounts` and `getUniqueRepos`. An entry that is not registered here does not exist on the site.

### `src/lib/`

Logic without UI, plus two browser hooks: the clipboard and the signed-in flag. All unit tests live here.

- `github.ts`: `getRepoStats`, `formatCount`, `formatRelativeDate`.
- `report.ts`: every export format: the JSON catalog (versioned by `CATALOG_VERSION`), the Markdown report, per-skill Markdown for "Copy for Claude", `llms.txt`, the cheat sheet and the install-all prompt.
- `recommend.ts`: the weighted token-overlap scorer behind `/recommend`.
- `selection.ts`: encodes and decodes the `sel` URL parameter.
- `site.ts`: site name, URLs and description, the operator's legal identity (`OPERATOR`, shown in the footer and on `/terms`), and `ariaCurrent` for nav links.
- `useCopyToClipboard.ts`: copy with transient "copied" feedback, shared by the copy buttons. The selection bar's "Copy share link" calls the clipboard API directly.
- `db/`: the `pg` pool and Drizzle client (`index.ts`), and the schema. `auth-schema.ts` is generated by the Better Auth CLI and never edited by hand; `schema.ts` re-exports it and defines the app's tables (`skill`, `skill_version`, `skill_file`, `report`, `username_hold`). Migrations live in `drizzle/`.
- `skills/`: SKILL.md parsing and the frontmatter rules (`schemas.ts`, YAML through `yaml`, checked with zod), the rules for a skill's other files and the folder picker's reader (`files.ts`), scan v1 (`scan.ts`, fixtures in `scan.fixtures.ts`), `access.ts` (`canRead`, `canEdit`, and `visibilityProblem`, the publishing gate), and the server side: `content-hash.ts`, `archive.ts` (a version as a zip, through `fflate`), `file-summaries.ts`, `queries.ts` (owner-scoped reads that answer 404, and `findVersionArchive`, the download's access check) and `actions.ts` (create, save a version, set the visibility, delete).
- `community/`: the Community pages' reads (`queries.ts`: no session, published skills of owners with a username only), `revalidateCommunity` (`revalidate.ts`), their addresses and the "Propose to the catalog" issue link (`links.ts`), their metadata, dates and cards (`metadata.ts`, `format.ts`), and the browser-side search (`search.ts`).
- `auth/`: the Better Auth config (`auth.ts`), the GitHub OAuth app's credentials (`github.ts`), the admins named by `ADMIN_USER_IDS` (`admin.ts`), the browser client and the `useAuthAction` hook its settings forms share, the sign-up allowlist and `isSignUpOpen`, profile cleaning, username and backup-code rules, the holds on given-up usernames (`username-hold.ts`), error messages for the forms and for `?error=` codes, the `signedIn` localStorage flag (`signed-in-flag.ts`), and the server side: `session.ts` (`getSession`, `requireSession`, `requireUser`), `queries.ts` (settings and export reads, never a token or hash), `actions.ts` (sign-out and session revoke) and `cleanup.ts` (the daily delete, unconfirmed accounts included).
- `moderation/`: reports and decisions: `schemas.ts` (the report form, a decision and its stated reason, the take-down form's target), `queries.ts` (`requireAdmin`, what a report can name, the admin page's lists), `actions.ts` (`submitReport`, `decideReport`, `takeDown`, `liftSuspension`) and `cleanup.ts` (reports decided a year ago).
- `cron.ts`, `timing.ts`, `rate-limit.ts`: the Vercel Cron secret check, the floor that pads password-reset requests, and the Upstash limits for Server Actions and downloads, with `visitorKey` for a visitor without an account.
- `email.ts`: plain-text templates, the moderation emails included, and `sendEmail`, which sends through Resend inside `after()`.

## Invariants

These hold today. Breaking one is an architecture decision, not a refactor: update this section in the same change.

1. **The catalog has no runtime backend.** Catalog pages and endpoints read only the registry and GitHub stats fetched at build or revalidation time. Their server code imports nothing from `src/lib/db` or `auth.ts`, and they set no cookie, so a database outage never reaches them. The five catalog pages export `dynamic = "error"`, so a request-time API there fails the build, and `e2e/anonymous.spec.ts` fails when a public page sets a cookie or calls `/api/auth`. The sitemap is the one shared route: per request, it adds the public Community pages from the database, and leaves them out when the read fails (invariant 23). RUNBOOK.md lists the secrets.
2. **The header asks for a session only after a sign-in.** `AccountSlot` loads `AccountMenu` through `next/dynamic`, and with it Better Auth's client and its `/api/auth/get-session` request, only while `localStorage.signedIn` is set. `/dashboard`, where every sign-in lands, sets it; sign-out and an empty session clear it. The layout's head script copies it to `data-signed-in` on `<html>`, so the menu's slot is reserved before hydration.
3. **GitHub is optional.** `getRepoStats` returns `null` on any failure (rate limit, 404, network error, malformed JSON) and never throws. Every consumer renders without stats, and a GitHub outage must never fail a build.
4. **One cache window, written in several places.** The 6-hour window is `REVALIDATE_SECONDS` in `github.ts` and the literal `21600` in each catalog route's `export const revalidate`. Next.js requires that value to be statically analyzable, so routes cannot import the constant. Change all of them together.
5. **The previous caching model.** `cacheComponents` is off. Caching uses route segment config (`revalidate`, `dynamic`) and `fetch(..., { next: { revalidate } })`. The matching docs are `node_modules/next/dist/docs/01-app/02-guides/caching-without-cache-components.md`. Do not add `"use cache"` without migrating on purpose.
6. **Deterministic serializers.** `report.ts` writes no timestamps by default (`generatedAt` defaults to `""`), so builds and tests are reproducible.
7. **`/skills` state lives in the URL.** `q`, `category` and `sel` are written with `window.history.replaceState`, not `router.replace`: the router call re-runs the async server page behind `<Suspense>` and flashes the skeleton on every click.
8. **Slugs are unique kebab-case** (`[a-z0-9-]+`). They are route params, sitemap entries and the `sel` encoding; `selection.ts` drops anything else.
9. **No AI call, and no third-party call while serving a catalog request.** GitHub is fetched at build and in background revalidation. The recommender and the selection export run in the browser; the other exports are built on the server at build or revalidation time. Account requests reach Postgres, Resend and Upstash only.
10. **`next build` needs no database.** The `pg` pool connects on its first query. `/community` queries while it prerenders, and every Community read goes through `emptyAtBuild` (`community/queries.ts`): during `next build` (`NEXT_PHASE`) a failed read renders the page empty. The e2e build proves it with `ACCOUNTS_OPEN=true` and a `DATABASE_URL` nothing answers.
11. **Sign-up is closed until launch.** Unless `ACCOUNTS_OPEN=true`, `databaseHooks.user.create.before` refuses every address outside `ACCOUNTS_ALLOWLIST`, for every sign-in method. It answers 400, because Better Auth turns a 403 into its generic "check your inbox" success.
12. **Auth requests go through `/api/auth`.** Better Auth's rate limit, stored in the `rate_limit` table, applies only there: an `auth.api` call on the server is never limited. So the forms use the browser client, and Server Actions never check a password: they sign out, and revoke sessions by deleting the signed-in user's rows by id.
13. **Authorization sits next to the data.** There is no `proxy.ts`. Every page, action and handler that needs a user checks the session itself, pages through `requireUser()`; layouts never check auth. Route handlers answer 401 instead of redirecting, and skill actions answer with a message, so an open editor keeps its text.
14. **Auth hosts are exact.** The auth base URL is the request host, accepted only when it is `localhost:3000` or one of Vercel's `VERCEL_PROJECT_PRODUCTION_URL`, `VERCEL_BRANCH_URL` and `VERCEL_URL`. A wildcard such as `*.vercel.app` would trust every Vercel deployment. GitHub callback URLs cannot be wildcards either, so GitHub sign-in exists only where `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` are set: production and localhost, each with its own OAuth app. The sign-in pages read them at build time, so a preview shows no GitHub button.
15. **A GitHub identity needs a verified email.** `user.validateUserInfo` refuses an unverified GitHub email before a user is created or linked, and on every GitHub sign-in: the allowlist would otherwise admit someone else's address. A failed GitHub sign-in lands on `/sign-in?error=<code>` (`onAPIError.errorURL`), which shows fixed text per code and never the URL's own `error_description`.
16. **Migrations only add, and the build applies them.** `vercel.json` runs `npm run db:migrate` before `next build` whenever `DATABASE_URL_UNPOOLED` is set. `scripts/migrate.mjs` calls drizzle's migrator directly, because `drizzle-kit migrate` 0.31 exits without printing the error. `0004` alone rewrote existing values, `content_hash`; RUNBOOK.md says what that means for a rollback.
17. **Auth logs carry no secrets.** `onAPIError.throw` hands unexpected errors to the wrapper in `api/auth/[...all]/route.ts`, which logs only the error's name and code. Left to Better Auth, a failed query is printed with its parameters: password hashes, reset and session tokens.
18. **No password exists before the address is proven.** Sign-up stores a random password the server picks (`hooks.before`), which nobody ever knows, and emails a single-use link; choosing the first password there confirms the address (`onPasswordReset`). Verification links go out only for an email change, never sign anyone in, and `beforeEmailVerification` deletes any password set before one is opened. Better Auth's new-address link still signs in the browser that opens it, after the current address has confirmed the change.
19. **Other sessions' tokens never reach the browser.** The settings page lists sessions from `queries.ts`, and `disabledPaths` turns off every endpoint that would list them or hand out OAuth tokens. `/get-session` still returns the current session's own token, which is useless without the signed cookie.
20. **A skill is changed only by its owner, and read by others only once published.** Skill actions match the skill's id and the signed-in user's id in the statement that writes, and dashboard reads pass the row through `canEdit`, so someone else's skill and its versions answer 404 and a replayed action writes nothing. The one exception is an admin's removal (invariant 25), which sets the status to `removed` and the reason the owner was given; the owner keeps reading, downloading and deleting the skill, and can never publish it again. Anyone else reads a skill only through `canRead`: published and not private, on the Community pages and as the zip download of its latest version, never an older one. `skill.owner_id` is `ON DELETE SET NULL` so that a sold skill can outlive its author, which is why `deleteUser.beforeDelete` deletes an account's skills first and the daily cleanup deletes any left without an owner.
21. **The scan flags; it never blocks a save, only publishing.** It runs in the editor on every change and again in the action, over SKILL.md and every text file, and the action stores the findings and the risk with each version. A latest version with a critical finding cannot be published (`visibilityProblem`), and a save that adds one to a published skill keeps the save and makes the skill private again, in the same transaction; both take the skill's row lock, so neither misses the other's version. A version holds at most 200 files and 1 MB, SKILL.md included, under the 2 MB Server Action body limit in `next.config.ts`; a save without a folder copies the latest version's files, so every version is complete. A skill keeps its latest 20 versions, and an account at most 50 skills, 1,500,000 characters of SKILL.md and 20 MB of files; every write takes an advisory lock on the account first, so saves at the same moment cannot pass these together. The data export gives each version's file count, size and download address instead of its files, which keeps it under Vercel's 4.5 MB response limit. The rate limit on Server Actions and downloads fails closed in production: without Upstash, on a Redis error or after its 3-second timeout, the request is refused.
22. **`content_hash` is the hash `npx skills` computes.** `content-hash.ts` gives the `computedHash` the skills CLI writes to skills-lock.json for the same folder: SHA-256 over each relative path and its bytes, the paths sorted by `localeCompare`. Path and bytes run together, so a save counts as unchanged only when the hash and every file's path and size match. An upload leaves out what the CLI leaves out when it installs or hashes (`.git`, `node_modules`, `__pycache__`, `__pypackages__`, `metadata.json`), refuses names with hidden or format characters, which would sort as equal, and paths that leave the folder never reach `skill_file`, whose CHECK refuses them too.
23. **Community shows published skills, and nothing until sign-up opens.** Its pages and the sitemap's Community entries exist only while `ACCOUNTS_OPEN=true`; before that they answer 404, and a download by anyone but the owner is refused. They show a published skill only when its owner has a username and is not suspended; the username is required to publish, and can then change but not be removed: public ones are listed in `/community`, on the author's profile and in the sitemap, and an unlisted one only at its own address, with `noindex`. An author's name and email never appear; the profile, which exists only with a public skill, shows the username and bio. The pages are ISR and read no session, so they set no cookie. Every write that changes what they show calls `revalidateCommunity()`, which marks all of them stale: publishing, a save or deletion of a published skill, a user update that sends a username or bio (`/update-user` is limited to 10 a minute), an account deletion, and every moderation decision that removes a skill or suspends or restores an account. The sitemap renders per request from a cached read, which the same call expires (`COMMUNITY_TAG`). A read that fails at request time throws, so ISR keeps serving the last page that rendered instead of caching an empty one or a 404.
24. **Anyone may download a published skill, at a limit.** A signed-out download is counted under `visitorKey`, an HMAC keyed with `BETTER_AUTH_SECRET` (it refuses to run without it) of the IPv4 address or the IPv6 /64, so Upstash never stores the address and one subscriber cannot rotate past the limit; a signed-in one under the user's id. The limit is checked only after `findVersionArchive` has allowed the download, so a refused request sends Upstash nothing. The version is then picked in a statement that checks again that the skill is published and its owner has a username and is not suspended, and its files, which never change, are read by that version's id.
25. **Moderation is a person's decision, and every decision states its reason by email.** Anyone can report: signed in through `/dashboard/report` (one open report per sender and target, at most 5 waiting per sender, rate-limited), or by email to the address in `OPERATOR`. Reports name only what Community shows: a published skill, or a profile with a public skill. Admins are told of a new report by email unless another one arrived within the hour. The admins are the user ids in `ADMIN_USER_IDS`; no role is stored, so a new user's `role` stays null, as Better Auth's generic answer to a sign-up with a taken address shows it. `/dashboard/admin` decides through Server Actions that check the admin first, and every endpoint of Better Auth's admin plugin is in `disabledPaths`: the actions call `auth.api.banUser` and `unbanUser` on the server with the admin's own session. A removal sets a published skill's status to `removed` with its stated reason; a suspension sets `user.banned`, deletes the account's sessions, and the plugin's `session.create.before` hook then refuses every sign-in method, GitHub and passkeys included, while `getSession` ignores a session that slipped in before the delete. An admin's account cannot be suspended. Each decision closes the open reports about its target (a suspension, those about the account's skills too), emails the affected account the statement of reasons (what, why, on which ground, whether a report led to it, that a person decided, how to contest it) and emails each closed report's sender the outcome; a dismissed report whose target is gone tells its sender so. The take-down form names an account only as `@username`. No email names the sender of a report or quotes it; an admin's stated reason is the one text a user did not write that reaches another user. A decided report is deleted after a year; the reports a user sent are in their data export.
26. **A username given up stays held for 90 days.** A rename holds the old username for its account, which keeps its 3 newest holds, and an account deletion holds its username for nobody (`username_hold`, user `SET NULL`). `databaseHooks.user.update.before` refuses a held username on `/update-user` unless the hold is the account's own, with the username plugin's own error, so a held name answers like one in use. Sign-up refuses a username, which is chosen in the settings, and an empty name before Better Auth answers a taken address, so neither refusal tells a taken address apart. `/is-username-available`, which would not know about holds, is disabled. The daily cleanup releases ended holds and deletes accounts whose address was not confirmed within 7 days of sign-up; such an account never signed in, so it owns nothing, and its username is not held.

## Cross-cutting concerns

- **Accessibility:** every page renders `SiteHeader`, `<main id="main">` and `SiteFooter`, and the layout's skip link targets `#main`. Nav links set `aria-current` through `ariaCurrent`. Motion honours `prefers-reduced-motion` in CSS and in `Reveal`, and a `scripting: none` rule keeps revealed content visible without JavaScript.
- **Theming:** dark by default, class strategy (`.dark` on `<html>`), choice stored in `localStorage.theme`. An inline script in `layout.tsx` applies it, and the `data-signed-in` mark, before first paint, which is why `<html>` carries `suppressHydrationWarning`.
- **SEO:** per-page `metadata` and `generateMetadata`, a sitemap and robots file generated from the registry and the public Community pages, an Open Graph image and `/llms.txt`. `SITE_URL` in `site.ts` is the canonical origin. Community pages set their own canonical address and `og:url` (`communityMetadata`), an unlisted skill's page `noindex`, and a SKILL.md's links `rel="nofollow ugc"`.
- **Accounts:** two-factor (TOTP and backup codes, stored encrypted) is asked on password sign-ins only: GitHub and passkeys verify the user their own way. A passkey works only on the host that registered it, must verify the person (fingerprint, face or PIN) when it is added and at every sign-in, and every new one is emailed to the owner. Adding one or disconnecting GitHub needs a sign-in from the last 5 minutes. GitHub never attaches itself to an existing account by email: it is connected from the settings. An email change is confirmed from the current address with a button, which a link scanner never presses. A password reset ends every session. Email-link tokens are stored hashed. The session cookie is `HttpOnly`, `Secure` and `SameSite=Lax`, and it is the only lasting cookie the site sets; a GitHub sign-in, a two-factor step and a passkey ceremony each add a cookie that lasts 10 minutes at most. Expired sessions and links, and rate-limit rows unused for a day, are deleted daily. GitHub access tokens are stored encrypted (`account.encryptOAuthTokens`). Account pages send `frame-ancestors 'none'` (`next.config.ts`).
- **Legal pages:** `/privacy` and `/terms` state what the code does: cookies, browser storage, providers, retention. A change to any of those updates them, and their date, in the same change.
- **User input:** `profile.ts` cleans every name to one line of at most 100 characters and drops any image that is not `https`, on sign-up and on update. Emails carry no text a user typed.
- **Testing:** Vitest in a Node environment over `src/**/*.test.ts`, for `src/lib`. Playwright tests in `e2e/` run against a production build on port 3000 with no database (a `DATABASE_URL` on a port nothing listens on) and Community open, and mock `/api/auth/get-session` where they need a session. The quality gates are AGENTS.md's commands.

## Known limits

- **GitHub rate limit.** Each 6-hour window costs one request per unique repo. The catalog has more unique repos than the 60 requests per hour GitHub allows without a token, so production needs `GITHUB_TOKEN` (5,000 per hour) or some cards lose their stats.
- **No fetch timeout.** `getRepoStats` handles errors, not slowness. A GitHub response that hangs past Next.js's 60-second static generation limit fails that page's build.
- **Recommender scale.** Token overlap is sized for tens to low hundreds of entries. Past that, a search index is the upgrade.
- **Community scale.** `/community` holds its 500 most recently changed public skills, and its search runs in the browser over those; past that it needs pagination or a search index. `revalidateCommunity()` marks every Community page stale on each write, which costs one render of each page visited afterwards; per-path invalidation is the upgrade if writes or pages grow.
- **Community during an outage.** A page that was never rendered, such as a skill's first visit, answers 500 while the database is down; pages already cached keep their last version.
- **Community abuse.** A signed-out download of any well-formed id costs one database lookup before the rate limit, and every limited request costs an Upstash command from the same database the Server Actions' limits use, so a flood could spend its quota. The guard is a Vercel Firewall rule that answers more than 20 requests a minute from one IP to `/api/skills/*/download` or `/sitemap.xml` with 429 before a function runs (RUNBOOK.md, "Edge rate limit"); a flood from many addresses still reaches Upstash. A username is held for 90 days after it is given up (invariant 26); after that, someone else can claim it with its old addresses.
- **Moderation by email.** Every moderation email goes through Resend, which delivers to the account owner's address only while `EMAIL_FROM` is its test sender, so before sign-up opens the sending domain must be set up or reports, receipts and statements of reasons reach nobody else. A report sent by email instead of the form is handled by hand (RUNBOOK.md, "Reports").
- **Scan v1 is pattern matching** over SKILL.md and every text file, line by line; a binary file is listed as not scanned. It flags what it recognises and cannot show that a skill is safe, so no screen says "safe"; a skill written to evade it can pass with no findings.
- **Open Graph image.** It uses the edge runtime, so it is rendered on demand; the build warns that the edge runtime disables static generation for that route.
- **Preview databases.** Neon's Vercel integration branches every preview from the project's default branch, which is `dev`: made-up accounts and skills from `scripts/seed-dev.mjs`, never a copy of production. Production keeps its own branch, `main`, which the integration's production-branch setting names. `dev` lags production's schema until it is migrated (RUNBOOK.md, "Preview databases"); each preview's build applies the missing migrations to its own branch. A preview's admin is the seeded `dev-admin`, which `ADMIN_USER_IDS` names in Preview.
