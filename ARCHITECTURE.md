# Architecture

How the Claude Skills Library is built. Read it before you change data flow, caching, routes or a shared module. What the product must do is in [PRD.md](PRD.md); how it looks is in [DESIGN.md](DESIGN.md).

Accounts, user skills, a marketplace, personal libraries and playbooks are being added phase by phase; [ROADMAP.md](ROADMAP.md) holds their target design. Everything below describes the code as it is, and each phase updates it when it changes the code.

## Bird's-eye view

A curated catalog of Claude Code skills, published as a mostly static Next.js site.

- **Input:** one hand-written TypeScript file per skill in `src/data/skills/`, plus repository stats from the GitHub REST API.
- **Output:** prerendered HTML pages and three plain-text or JSON endpoints, regenerated every 6 hours (ISR).
- **The catalog has no backend.** Search, filters, multi-select, the recommender, copy and download run in the browser on data already in the page.
- **Accounts have one:** Postgres on Neon through Drizzle, and Better Auth for email and password and GitHub sign-in. Only `/api/auth`, the sign-in pages, `/dashboard` and the header's account menu reach it, and the menu loads only in a browser that has signed in before.

```text
src/data/skills/<slug>.ts ──► src/data/skills/index.ts      registry: skills[] + helpers
                                         │
api.github.com ◄── src/lib/github.ts ────┤                  one fetch per unique repo,
                                         │                  cached 6 h, null on any failure
                                         ▼
                  src/app/**   Server Components and route handlers
                  ├── HTML pages ──► client components: search, selection, recommender, copy, download
                  └── /skills.json · /llms.txt · /install-all.txt     serializers in src/lib/report.ts
```

## Code map

### `src/data/`

- `types.ts`: the `Skill` interface, `SkillCategory`, `InstallMethod` and `CATEGORY_LABELS`. Every entry, page and serializer depends on this schema.
- `skills/<slug>.ts`: one catalog entry per file, exported as `export const skill: Skill`.
- `skills/index.ts`: the registry. It imports every entry into `skills` (lists sort by GitHub stars, so array order only breaks ties) and exposes `getSkill`, `getFeaturedSkills`, `getCategoriesWithCounts` and `getUniqueRepos`. An entry that is not registered here does not exist on the site.

### `src/lib/`

Logic without UI, plus two browser hooks: the clipboard and the signed-in flag. All unit tests live here.

- `github.ts`: `getRepoStats`, `formatCount`, `formatRelativeDate`.
- `report.ts`: every export format: the JSON catalog (versioned by `CATALOG_VERSION`), the Markdown report, per-skill Markdown for "Copy for Claude", `llms.txt`, the cheat sheet and the install-all prompt.
- `recommend.ts`: the weighted token-overlap scorer behind `/recommend`.
- `selection.ts`: encodes and decodes the `sel` URL parameter.
- `site.ts`: site name, URLs and description, the operator's legal identity (`OPERATOR`, shown in the footer and on `/terms`), and `ariaCurrent` for nav links.
- `useCopyToClipboard.ts`: copy with transient "copied" feedback, shared by the copy buttons. The selection bar's "Copy share link" calls the clipboard API directly.
- `db/`: the `pg` pool and Drizzle client (`index.ts`), and the schema. `auth-schema.ts` is generated by the Better Auth CLI and never edited by hand; `schema.ts` re-exports it. Migrations live in `drizzle/`.
- `auth/`: the Better Auth config (`auth.ts`), the GitHub OAuth app's credentials (`github.ts`), the browser client, the sign-up allowlist, profile cleaning, error messages for the forms and for `?error=` codes, the `signOut` Server Action, the `signedIn` localStorage flag (`signed-in-flag.ts`), and `session.ts`, the server-only `getSession` and `requireUser`.
- `email.ts`: plain-text templates and `sendEmail`, which sends through Resend inside `after()`.

### `src/app/`

| Route | Source | Rendering |

### `src/components/`

One component per file, named export. Client components (`"use client"`): `SkillSearch`, `SelectionBar`, `SkillRecommender`, `HeroSearch`, `HeroInstall`, `ThemeToggle`, `NavLink`, `Reveal`, `CopyButton`, `CopyForClaudeButton`, `DownloadButton`, and in `auth/` the four forms, `AccountSlot`, `AccountMenu`, `GitHubSignInButton`, `OAuthError`, `SignOutButton` and `SignedInMarker`. The rest render on the server; `SkillCard` and `StatsRow` also ship to the browser, because `SkillSearch` and `SkillRecommender` import them.

## Invariants

These hold today. Breaking one is an architecture decision, not a refactor: update this section in the same change.

1. **The catalog has no runtime backend.** Catalog pages and endpoints read only the registry and GitHub stats fetched at build or revalidation time. Their server code imports nothing from `src/lib/db` or `auth.ts`, and they set no cookie, so a database outage never reaches them. The five catalog pages export `dynamic = "error"`, so a request-time API there fails the build, and `e2e/anonymous.spec.ts` fails when a public page sets a cookie or calls `/api/auth`. RUNBOOK.md lists the secrets.
2. **The header asks for a session only after a sign-in.** `AccountSlot` loads `AccountMenu` through `next/dynamic`, and with it Better Auth's client and its `/api/auth/get-session` request, only while `localStorage.signedIn` is set. `/dashboard`, where every sign-in lands, sets it; sign-out and an empty session clear it. The layout's head script copies it to `data-signed-in` on `<html>`, so the menu's slot is reserved before hydration.
3. **GitHub is optional.** `getRepoStats` returns `null` on any failure (rate limit, 404, network error, malformed JSON) and never throws. Every consumer renders without stats, and a GitHub outage must never fail a build.
4. **One cache window, written in several places.** The 6-hour window is `REVALIDATE_SECONDS` in `github.ts` and the literal `21600` in each catalog route's `export const revalidate`. Next.js requires that value to be statically analyzable, so routes cannot import the constant. Change all of them together.
5. **The previous caching model.** `cacheComponents` is off. Caching uses route segment config (`revalidate`, `dynamic`) and `fetch(..., { next: { revalidate } })`. The matching docs are `node_modules/next/dist/docs/01-app/02-guides/caching-without-cache-components.md`. Do not add `"use cache"` without migrating on purpose.
6. **Deterministic serializers.** `report.ts` writes no timestamps by default (`generatedAt` defaults to `""`), so builds and tests are reproducible.
7. **`/skills` state lives in the URL.** `q`, `category` and `sel` are written with `window.history.replaceState`, not `router.replace`: the router call re-runs the async server page behind `<Suspense>` and flashes the skeleton on every click.
8. **Slugs are unique kebab-case** (`[a-z0-9-]+`). They are route params, sitemap entries and the `sel` encoding; `selection.ts` drops anything else.
9. **No AI call, and no third-party call while serving a catalog request.** GitHub is fetched at build and in background revalidation. The recommender and the selection export run in the browser; the other exports are built on the server at build or revalidation time. Account requests reach Postgres and Resend only.
10. **`next build` needs no database.** The `pg` pool connects on its first query, and no prerendered page queries.
11. **Sign-up is closed until launch.** Unless `ACCOUNTS_OPEN=true`, `databaseHooks.user.create.before` refuses every address outside `ACCOUNTS_ALLOWLIST`, for every sign-in method. It answers 400, because Better Auth turns a 403 into its generic "check your inbox" success.
12. **Auth requests go through `/api/auth`.** Better Auth's rate limit, stored in the `rate_limit` table, applies only there: an `auth.api` call on the server is never limited. So the forms use the browser client, and Server Actions call `auth.api` only where no password is involved, such as sign-out.
13. **Authorization sits next to the data.** There is no `proxy.ts`. Every page, action and handler that needs a user calls `requireUser()`; layouts never check auth.
14. **Auth hosts are exact.** The auth base URL is the request host, accepted only when it is `localhost:3000` or one of Vercel's `VERCEL_PROJECT_PRODUCTION_URL`, `VERCEL_BRANCH_URL` and `VERCEL_URL`. A wildcard such as `*.vercel.app` would trust every Vercel deployment. GitHub callback URLs cannot be wildcards either, so GitHub sign-in exists only where `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` are set: production and localhost, each with its own OAuth app. The sign-in pages read them at build time, so a preview shows no GitHub button.
15. **A GitHub identity needs a verified email.** `user.validateUserInfo` refuses an unverified GitHub email before a user is created or linked, and on every GitHub sign-in: the allowlist would otherwise admit someone else's address. A failed GitHub sign-in lands on `/sign-in?error=<code>` (`onAPIError.errorURL`), which shows fixed text per code and never the URL's own `error_description`.
16. **Migrations only add, and the build applies them.** `vercel.json` runs `npm run db:migrate` before `next build` whenever `DATABASE_URL_UNPOOLED` is set. `scripts/migrate.mjs` calls drizzle's migrator directly, because `drizzle-kit migrate` 0.31 exits without printing the error.
17. **Auth logs carry no secrets.** `onAPIError.throw` hands unexpected errors to the wrapper in `api/auth/[...all]/route.ts`, which logs only the error's name and code. Left to Better Auth, a failed query is printed with its parameters: password hashes, reset and session tokens.

## Cross-cutting concerns

- **Accessibility:** every page renders `SiteHeader`, `<main id="main">` and `SiteFooter`, and the layout's skip link targets `#main`. Nav links set `aria-current` through `ariaCurrent`. Motion honours `prefers-reduced-motion` in CSS and in `Reveal`, and a `scripting: none` rule keeps revealed content visible without JavaScript.
- **Theming:** dark by default, class strategy (`.dark` on `<html>`), choice stored in `localStorage.theme`. An inline script in `layout.tsx` applies it, and the `data-signed-in` mark, before first paint, which is why `<html>` carries `suppressHydrationWarning`.
- **SEO:** per-page `metadata` and `generateMetadata`, a sitemap and robots file generated from the registry, an Open Graph image and `/llms.txt`. `SITE_URL` in `site.ts` is the canonical origin.
- **Accounts:** an email must be verified before its first sign-in, and the verification link signs the user in. A password reset ends every session. Reset and verification tokens are stored hashed. The session cookie is `HttpOnly`, `Secure` and `SameSite=Lax`, and it is the only lasting cookie the site sets; a GitHub sign-in adds a short-lived OAuth state cookie. GitHub access tokens are stored encrypted (`account.encryptOAuthTokens`). Account pages send `frame-ancestors 'none'` (`next.config.ts`).
- **Legal pages:** `/privacy` and `/terms` state what the code does: cookies, browser storage, providers, retention. A change to any of those updates them, and their date, in the same change.
- **User input:** `profile.ts` cleans every name to one line of at most 100 characters and drops any image that is not `https`, on sign-up and on update. Emails carry no text a user typed.
- **Testing:** Vitest in a Node environment over `src/**/*.test.ts`, for `src/lib`. Playwright tests in `e2e/` run against a production build on port 3000 with no database, and mock `/api/auth/get-session` where they need a session.
- **Quality gates:** `npm test`, `npm run lint`, `npx tsc --noEmit`, `npm run build`, `npm run test:e2e`.

## Known limits

- **GitHub rate limit.** Each 6-hour window costs one request per unique repo. The catalog has more unique repos than the 60 requests per hour GitHub allows without a token, so production needs `GITHUB_TOKEN` (5,000 per hour) or some cards lose their stats.
- **No fetch timeout.** `getRepoStats` handles errors, not slowness. A GitHub response that hangs past Next.js's 60-second static generation limit fails that page's build.
- **Recommender scale.** Token overlap is sized for tens to low hundreds of entries. Past that, a search index is the upgrade.
- **Open Graph image.** It uses the edge runtime, so it is rendered on demand; the build warns that the edge runtime disables static generation for that route.
- **Preview databases.** Neon's Vercel integration branches every preview from the production branch, so a preview holds a copy of production accounts. Accepted while sign-up is invite-only; ROADMAP.md P7 moves previews to a seeded `dev` branch.
